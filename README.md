# 分代 GC 仿真与参数调优工具

一个纯 Python（3.9 + numpy）的分代垃圾回收器仿真器、调参器与反向校准工具，
附带一个完全离线的 HTML 看板。它回答的问题是：**为什么参数换了又换，停顿
还是过几天就回来？**

核心结论在模型里是可复现的：新生代大小决定 minor 的频率与单次拷贝量，晋升
年龄阈值决定中等寿命对象何时进入老年代，而**并发标记速率一旦低于晋升速率，
并发回收就必然退化成全堆停顿**——这条退化条件与流量高峰耦合，所以“低谷没
问题、高峰就长停顿”。工具把这条链条拆成可观测的量，并给出每个参数改动的
量化后果。

## 1. 仿真模型

### 1.1 堆结构

```
┌───────────── 新生代 young ─────────────┐   ┌──── 老年代 old ────┐
│   eden（分配区）  │ survivor A │ survivor B │   │  长期存活对象       │
└───────────────────┴────────────┴────────────┘   └────────────────────┘
```

* 对象只在 eden 中分配；
* 新生代回收（minor）时仍然活着的 eden 对象被拷贝进存活区，存活区里已有对
  象年龄 +1；
* 年龄超过 `tenuring_threshold` 的对象晋升到老年代；
* **存活区放不下时，最老的对象被提前晋升**（age < 阈值）——这就是“过早晋
  升”，也是中等寿命对象慢慢填满老年代的机制；
* 引用环不可达即垃圾：对象是否存活由“死亡时间”决定，与真实追踪式回收器一
  致；
* **浮动垃圾**：老年代里已死但尚未被回收的对象仍然占用空间，直到下一次老
  年代回收才被清扫。

### 1.2 停顿模型

新生代停顿与“需要拷贝的存活对象”成正比：

```
t_minor = minor_fixed + per_byte × 拷贝字节 + per_object × 拷贝个数
```

全堆停顿（mark-compact）：

```
t_full = full_fixed + per_byte × 存活字节 + per_object × 存活个数
```

并发周期：初始标记短暂停顿 → 并发标记（与应用并行）→ 重标记短暂停顿。
并发标记占用 CPU，代价与标记速率成正比（单核扫描速率有限，最多 4 核）。

### 1.3 并发退化的建模（重点）

每开始一个并发周期，记录当时老年代的存活量 `work`；周期运行期间应用仍在晋
升对象，晋升速率用 EWMA 估计为 `growth`，每次晋升还会因写屏障增加标记债
务。判据是**投影占用**：

```
net = mark_rate − barrier_slope × growth
finish = (work − 已标记量) / net
projected = old_used + growth × finish
若 projected ≥ panic_ratio × old_capacity → 退化为全堆停顿
```

即“标记追不上晋升与分配”。此外还有两条触发路径：进入周期时已经越过 panic
线（`degen-start`）、周期运行中越过 panic 线（`degen-panic`）、以及池子耗
尽/晋升失败。日志里会区分这些原因。

### 1.4 对象寿命分布

三类对象，寿命为 Weibull 分布 `S(t)=exp(-(t/scale)^shape)`：

| 类别 | 形状 | 典型中位寿命 | 行为 |
|------|------|--------------|------|
| 请求对象 | shape≈0.5–0.6（重尾） | 毫秒级 | 几乎都在新生代内死亡 |
| 会话对象 | shape≈1.1–1.7 | 20 s – 2 min | **中等寿命，最容易被过早晋升** |
| 缓存对象 | shape≈4–6（集中） | 数分钟 – 数十分钟 | 长期存活，直接占老年代 |

参数由 `ObjectPopulation` 定义，可改份额、尺度、形状和平均大小。它们不是拍脑袋
填的，而是可以从服务行为里 **拟合** 出来的（`gcsim/fitting.py`）：

```bash
# 从分配采样（CSV：lifetime_s,size_bytes[,class]）拟合三类对象
python3 -m gcsim.cli fit-population --input samples/object-lifetime-trace.csv

# 从一份 GC 日志反推寿命曲线（可保留已知的类别构成，只重估寿命）
python3 -m gcsim.cli fit-from-log --log samples/trading-gateway-1h.simple.log \
        --scenario trading-gateway
```

`fit_population` 在 log 寿命 / log 大小两维上做高斯混合（EM）聚类，按中位寿命
排序成 请求 / 会话 / 缓存 三类，再对每一类做 Weibull 生存曲线与对数正态大小
的拟合。样例轨迹的拟合结果：请求 88.2% / 中位 3.5 ms、会话 8.9% / 中位 20 s、
缓存 3.0% / 中位 273 s，与生成轨迹的真值（88% / 9% / 3%，尺度 4 ms / 25 s /
300 s）一致。

从 GC 日志反推寿命只能给出**区间**：幸存区溢出会把仍存活的对象提前晋升、移出
幸存区，所以“下一轮幸存的字节数”会低估存活率。工具因此输出
`one_step_lower` / `one_step_upper` 与 `overflow_dominated` 标记，并在 CLI 输出
里写明这一点；需要精确分布时应使用对象寿命轨迹。

### 1.5 流量曲线

一整天 86400 秒，按小时给出 24 个倍率（夜间低谷 → 早盘 → 午间回落 → 午后
高峰 → 收盘脉冲），再用 Ornstein–Uhlenbeck 过程叠加突发波动。分配速率 =
背景速率 + (峰值速率 − 背景速率) × 曲线倍率，突发系数直接影响分配速率的
短期波动。

### 1.6 采样：怎么做到一天几秒

真实服务一天分配几十亿个对象，逐对象仿真不现实。引擎只对**熬过新生代回收
的对象**建立带权重的记录：同一类对象在同一次收集里共享一个权重 `w`，表示
每个样本代表多少个真实对象。`Σ w·size` 即真实存活字节。存活区溢出、晋升
阈值、浮动垃圾、并发债务全部在真实状态上计算，不是平均场近似。

> 校验：分配总量与流量积分一致（误差 < 2%）；`max_records_per_minor` 从
> 400 降到 20，晋升速率估计偏差 < 35%，量级不变（见测试）。

## 2. GC 日志

### 2.1 写出

两种方言，`render_hotspot()` 与 `render_simple()`：

```
[2026-11-21T17:27:29.884+0800][info][gc,start    ] GC(5754) Pause Full (Allocation Stall)

[2026-11-21T17:27:29.884+0800][info][gc,phases   ] GC(5754)   Mark Live Objects: 417.8ms
[2026-11-21T17:27:29.884+0800][info][gc,phases   ] GC(5754)   Pause Full (Allocation Stall) 673.9ms
[2026-11-21T17:27:29.884+0800][info][gc,heap     ] GC(5754) Heap after full GC: live 1394.6 MiB
```

```
YOUNG t=12.340 pause=6.700 eden=48.0->0.0 surv=3.0->4.0 old=612.0->655.0 promoted=7.2 tenuring=6
```

### 2.2 读入与反演

`parse_log()` 自动识别方言，`estimate_parameters()` 从日志估计：

* **分配速率** = Σ eden 回收前占用 / 窗口时长（精确到 0.1%）；
* **晋升速率** = Σ 每次 minor 的晋升量 / 窗口（或 old 区增量）；
* **存活集** = full GC 后老年代占用；
* **各代容量** = eden/survivor 区容量的众数；
* **晋升阈值** = 日志中 desired threshold 的众数（自适应策略取后半段）；
* **并发标记速率** = (存活集 + 晋升速率 × 周期时长) / 周期时长，用完成的并
  发周期估计；
* **停顿模型系数** = 对 `pause = a + b·拷贝字节` 做最小二乘，给出 R² 与
  可辨识性（若某类收集的存活集几乎恒定，斜率会被标为“不可辨识”而非硬猜）。

> 实测（`samples/trading-gateway-1h.hotspot.log`，基线配置）：
>
> | 量 | 真值 | 从日志估出 |
> |---|---|---|
> | 分配速率 | — | 18.2 MiB/s（与仿真总量一致） |
> | 晋升速率 | — | 4.90 MiB/s |
> | eden / 幸存区 | 48 / 4 MiB | 48 / 4 MiB |
> | 晋升阈值 | 6 | 6 |
> | young 停顿模型 | 0.6 ms + 0.367 ms/MiB | 0.629 ms + 0.367 ms/MiB，R²=0.997 |
> | full 停顿模型 | 10 ms + 0.472 ms/MiB | 9.94 ms + 0.473 ms/MiB，R²=1.000 |
>
> 完整对照见 `reports/acceptance.json` 中每个场景的 `calibration` 段（含真值）。

## 3. 调参

### 3.1 目标

* 最长停顿 ≤ `pause_target_ms`（默认 25 ms）；
* 吞吐损失 ≤ `1 - throughput_target`（默认 3%）；
* 超预算请求占比 ≤ `tail_frac`（默认 0.2%）；
* **总堆不超过 `max_heap_mib`**（`trading-gateway` / `order-lifecycle` 6 GiB，
  `market-data` 8 GiB）。

最后一条是刻意的约束：靠加内存换停顿不算调参。把老年代从 3 GiB 抬到 24 GiB
当然能让长停顿消失，但交易前置服务的机器不会因此变便宜。工具在预算内寻找
“真的改变了机制”的解。

### 3.2 搜索

1. **粗筛**：在 **两个对比时段**（最忙的一小时 + 傍晚仍忙的一小时）上并行
   评估结构化网格（新生代尺寸×幸存区×阈值、老年代容量、并发触发比×标记速
   率三块，而非全笛卡尔积），取两个窗口里更差的那个计分——退化不只发生在
   最高峰；
2. **复评**：入围的 24 个候选先按尺寸组合去重（避免全部挤在空间的同一个
   角落），再在完整一天上、多个随机种子上各跑一遍；
3. **精调**：对最差的 4–6 个候选做坐标下降，每次只动一个参数。

每一步都用 **多个随机种子** 各跑一遍完整一天，按 **最差的那一天** 排序。原因很
实际：流量是随机的，只在单次仿真里“刚好躲过”退化的参数，换一天就会复发——
这正是“参数换了过两天又出现长停顿”的仿真版本。

### 3.3 每个参数改动的后果（单因子消融）

对推荐配置逐参数左右各移一档，其余不变，报告 Δ 最长停顿、Δ 全堆停顿次数、
Δ 吞吐损失、Δ 晋升速率，并给出机制解释。为了消除随机突发带来的噪声，这一
组对比关闭突发系数。

一条实测结论（`trading-gateway`）：把并发标记速率从 ~15 MiB/s 提到 ≥64
MiB/s，或把触发比例从 0.5 降到 0.45，全堆停顿次数从 58 降到 0；而单纯减小
eden 只会让 minor 更频繁、吞吐略降，长停顿仍然存在。

## 4. 验收

三个内置服务（`gcsim/config.py`）：

| 场景 | 对象构成 | 流量特征 |
|------|----------|----------|
| `trading-gateway` | 88% 请求 / 9% 会话 / 3% 缓存，会话中位 ~20 s | 双峰交易日 + 收盘脉冲 |
| `market-data` | 82% / 15% / 3%，会话中位 ~34 s，突发系数 0.55 | 高突发，晚间长尾 |
| `order-lifecycle` | 76% / 21% / 3%，会话中位 ~90 s（分钟级） | 中等突发，平稳 |

每个场景输出：

* 停顿分布（P50/P95/P99/P99.9/最长）与按时长分桶的直方图；
* 吞吐损失（STW + 并发 CPU 占比）；
* 全堆停顿次数及其原因分解（并发退化 / 晋升失败 / 池耗尽）；
* 调优前后对比；
* 反向校准表（估出的参数 vs 真实设置）。

看板展示：各代占用随时间的变化、每次回收的停顿、对象年龄分布、调参前后对
比、每个参数改动的后果、反向校准结果。

## 6. 局限

* 对象图被抽象为“死亡时间”，不建模跨代引用的具体拓扑；写屏障开销以系数
  形式计入并发债务。
* 老年代分区（region）以 1 MiB 粒度向日志呈现，内部按字节建模。
* 会话语义（请求延迟 → 超时）用“请求均匀到达、被停顿挡住的时间”估算，属
  于解析近似，不是排队仿真。
* 反向校准的“不可辨识”标注是刻意的：当所有 full GC 都在同一存活集上触发
  时，不假装能估出斜率。
