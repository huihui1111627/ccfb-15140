# 技术说明：为什么会长停顿，以及参数到底在影响什么

这份说明配合 `README.md` 阅读。它回答三个问题：

1. 模型里有哪些机制，每个机制对应真实回收器的哪一部分；
2. 反向校准能还原到什么精度、哪些量在什么条件下不可辨识；
3. 三个验收服务上，参数搜索找到了什么，以及每个参数改动带来的后果。

---

## 1. 长停顿的机制链条

验收里的基线配置是刻意设置的“典型病态”。它的过程如下：

```
会话对象中位寿命 20s–90s
        │  新生代回收间隔在高峰时只有 2–5s
        ▼
对象在幸存区熬不到晋升阈值 → 幸存区溢出
        ▼
最老的对象被提前晋升（age < 阈值）→ 老年代以晋升速率 g 增长
        ▼
老年代越过并发触发比例 → 启动并发标记，标记速率 m
        ▼
若 m 追不上 g（写屏障债务让有效速率更低），投影占用在周期结束前越过 panic 线
        ▼
并发周期退化为全堆停顿式回收 → 一次几百毫秒到 1.3 秒的停顿
```

关键判据在 `engine.py::_cycle_projection`：

```
net       = m − barrier_slope × g
finish    = (work − marked) / net
projected = old_used + g × finish
若 projected ≥ panic_ratio × old_capacity → 退化
```

这是“标记追不上分配/晋升”的直接建模。它解释了两个现象：

* **为什么低谷时没问题**：g 低，投影不会越过 panic 线；
* **为什么“换参数”可能只是把问题推后**：只要 m 与 g 的关系没变，下一次高峰
  还会越线。压低 eden 让 minor 更频繁，只是把同样的晋升量摊到更多次回收里。

## 2. 各参数在机制上的作用

| 参数 | 直接作用 | 副作用 | 搜索中的典型结论 |
|------|----------|--------|------------------|
| eden | 决定 minor 间隔与单次拷贝量 | 越大越少回收，但单次停顿更长 | 单独调 eden 不能消除长停顿 |
| survivor | 决定对象能熬几轮 | 过小 → 提前晋升；过大 → 挤压 eden | survivor 与阈值必须一起调 |
| 晋升阈值 | 决定何时进入老年代 | 提高会拉长幸存区拷贝 | 对分钟级会话对象，阈值再高也救不了 |
| 老年代容量 | 只改变 full/并发触发时机 | 越大触发越晚、单次标记越大 | 在堆预算内是有限的杠杆 |
| 并发触发比例 | 决定并发周期的起跑时间 | 越低越安全，但周期更频繁、CPU 更贵 | 0.45→0.6 是常见的安全区 |
| 并发标记速率 | 直接决定 m 与 g 的关系 | 标记线程占用 CPU | **最关键**；m < g 时必然退化 |

单因子消融表（看板的“调参”页）就是从推荐配置出发，每次只动一个参数，报告
Δ 最长停顿、Δ 全堆停顿次数、Δ 吞吐损失、Δ 晋升速率，并附上机制解释。这些解释
都是先报实测数字，再讲机制，不会预测与数字相反的方向。

## 3. 反向校准

`gclog.py` 的解析器独立于写出器：它只读取行文本，不共享模拟器的内部状态。能
从日志还原的量与实测精度（三个场景，共 6 份日志）：

| 量 | 方法 | 实测相对误差 |
|----|------|--------------|
| 分配速率 | Σ eden 回收前占用 / 窗口 | < 0.1% |
| 晋升速率 | Σ 每次 minor 的晋升量 / 窗口 | < 0.5% |
| eden / survivor 容量 | 日志中区容量的众数 | 精确 |
| 晋升年龄阈值 | desired threshold 众数（自适应取后半段） | 精确 |
| young GC / full GC / 退化次数 | 事件计数 | 精确 |
| 并发标记速率 | (周期结束后的存活集 + 晋升速率×周期时长) / 周期时长 | 通常 < 10% |
| young 停顿模型 | 对 `pause = a + b×拷贝字节` 最小二乘 | a、b 误差 < 2%，R² ≈ 0.99 |
| full 停顿模型 | 对 `pause = a + b×存活字节` 最小二乘 | 同上 |

“不可辨识”的标注是刻意保留的：

* 若调优后不再发生 full GC，full 停顿模型就**没有数据可拟合**，工具会明确
  显示“本次运行未出现该现象，无法估计”，而不是给出一个凭空的数；
* 若某类收集的存活集几乎恒定（例如所有 full GC 都由同一个 panic 阈值触发），
  固定开销与斜率在统计上不可分离，工具会标为“斜率不可辨识”。

## 4. 采样与统计

一天的真实分配量在几十亿对象量级，逐对象仿真不可行。引擎只对熬过新生代回收
的对象建立**带权重**的记录，权重表示一个样本代表多少真实对象。这样：

* 分配总量按流量曲线精确积分；
* 存活区溢出、晋升、浮动垃圾、并发债务都在真实状态上计算；
* 记录数上限（`max_records_per_minor`）只影响内存，不影响量级。

测试 `test_promotion_rate_is_unbiased_by_record_cap` 验证了记录上限从 400 降到
20 时晋升速率偏差 < 35%。验收使用更大的 `record_cap`，误差进一步减小。

由于流量带有随机突发，**单次一天的仿真只是一个样本**。搜索在最后的候选阶段
会用多个随机种子（默认 3 个）各跑一整天，按“最差的那一天”排序；验收报告里的
“调优前/后”则是固定种子下的完整一天。这正是“参数过两天又复发”的仿真对应物。

搜索本身还有一条工程约束：**总堆不超过场景预算**。不加这条约束，搜索会把老
年代一路加到 24 GiB——长停顿当然消失，但那只是花更多内存买来的，不是调参。

## 5. 验收结果（`reports/acceptance.json`）

目标：最长停顿 ≤ 25 ms，吞吐损失 ≤ 3%，超预算请求 ≤ 0.2%，总堆 ≤ 场景预算。

三个场景的基线都表现出同一个病态（固定种子、默认参数、一整天）：

| 服务 | 最长停顿 | P99 停顿 | 全堆停顿 | 其中退化 | 吞吐损失 | 主要原因 |
|---|---|---|---|---|---|---|
| trading-gateway | 653 ms | 7.4 ms | 179 | 179 | 0.40% | 并发标记跟不上 |
| market-data | 1259 ms | 591.8 ms | 707 | 707 | 1.26% | 并发标记跟不上 |
| order-lifecycle | 885 ms | 874.7 ms | 1403 | 1403 | 1.75% | 并发标记跟不上 |

并发标记速率（15–19 MiB/s）低于高峰晋升速率，全天几百到一千多次退化。搜索后
在预算内找到的解都大幅提高了标记速率或提前触发并发周期，同时适度调整了新生代
尺寸。

具体数字由 `reports/acceptance.json` 与 `reports/dashboard.html` 给出（每次
运行会略有不同，因为流量是随机的）。看板“总览”页把调优前后并排列出，
“调参”页给出推荐参数与逐参数后果，“反向校准”页给出真值与估计值的对照。

### 最终验收结果

| 服务 | 最长停顿 (前) | 最长停顿 (后) | P99 (后) | 全堆停顿 (前→后) | 吞吐损失 (后) |
|---|---|---|---|---|---|
| trading-gateway | 653 ms | 22.0 ms | 20.3 ms | 179 → 0 | 0.32% |
| market-data | 1259 ms | 28.3 ms | 23.9 ms | 707 → 0 | 0.99% |
| order-lifecycle | 885 ms | 19.6 ms | 16.8 ms | 1403 → 0 | 0.40% |

反向校准（调优后）：trading-gateway 12/12；market-data 12/12；order-lifecycle 12/12。
